# Going Further: `clock_gettime` and `time`

## Things to try

1. **Count the syscalls, both ways.**
   The raw version shows two `clock_gettime` lines under `strace`; the libc version shows **none**.
   The reason is the vDSO — see the discussion below and the `README.md`.

1. **Compare the clocks.**
   Read `CLOCK_REALTIME` and `CLOCK_MONOTONIC` together, step the system clock with `date -s`, and read again.
   `CLOCK_REALTIME` jumps; `CLOCK_MONOTONIC` does not.
   Note that `CLOCK_MONOTONIC` counts from an unspecified origin (boot, in practice), so its absolute value is meaningless — only differences are.

1. **Time something with the wrong clock.**
   Measure a one-second sleep with `CLOCK_REALTIME` while stepping the clock backwards.
   The elapsed time comes out negative.
   This is the bug `CLOCK_MONOTONIC` exists to prevent, and it is why it appears in every serious timing library.

1. **Measure the resolution.**
   The smallest non-zero difference between consecutive readings is typically tens of nanoseconds via the vDSO, and larger through the raw syscall — because the syscall overhead itself exceeds the clock's granularity.
   `clock_getres(2)` reports 1 ns, which is the *representable* resolution, not the achievable one.

1. **`CLOCK_PROCESS_CPUTIME_ID` and `CLOCK_THREAD_CPUTIME_ID`** measure CPU time consumed rather than time elapsed.
   Their sum across a run corresponds to the `user` + `sys` columns from `time`.
   A sleeping process advances `CLOCK_REALTIME` but not these.

## Questions to answer

* **Why is `tp` an output parameter rather than a return value?**
  A system call returns one machine word.
  A `struct timespec` is two, so it cannot be returned in a register; the kernel writes it into caller-supplied memory instead.
  Any syscall returning more than one word does the same.

* **Why does `time()` both return the value and store it through a pointer?**
  Historical accident, inherited from V7 Unix and preserved for compatibility.
  Nobody would design it that way today; the pointer form predates the convention that a `time_t` could simply be returned.

* **Does `my_time()` truncate or round?**
  Truncates, by discarding `tv_nsec` — and so does glibc.
  `time()` is specified to return the number of *whole* seconds elapsed, so truncation is correct.

* **Which clock for a log timestamp, which for a duration?**
  `CLOCK_REALTIME` for a timestamp that must mean something to a human.
  `CLOCK_MONOTONIC` for any duration.

## Discussion points

* **This is where "syscalls always enter the kernel" stops being true.**
  Linux maps the **vDSO** into every process: a small shared object, generated by the kernel, containing code that reads the time from a page the kernel keeps updated.
  libc's `clock_gettime()` runs that code and never changes privilege level, which is why `strace` shows nothing.
  `ldd` on any dynamically linked binary lists `linux-vdso.so.1` with no path — it is not a file on disk.
* **The raw-syscall version in this exercise is therefore slower than libc's.**
  That is the point, not a defect.
  Same trade as buffering in session 01: the fast path wins by *avoiding* the expensive operation.
* **`CLOCK_REALTIME` can move backwards.**
  NTP steps it, administrators set it.
  Durations measured with it can be negative, and the resulting bugs surface twice a year.
* **Not every syscall can be accelerated this way.**
  The vDSO only works for operations that are read-only and need no privilege — reading a clock, getting the CPU number.
  Anything that changes kernel state must still cross the boundary.
