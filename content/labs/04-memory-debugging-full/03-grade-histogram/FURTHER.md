# Going Further: The Histogram That Counts Too Much

## Things to try

1. **Rebuild with AddressSanitizer** and rerun the buggy version:

   ```console
   gcc -Wall -Wextra -g -O0 -fsanitize=address -o histogram main.c
   ./histogram < input.txt
   ```

   It reports nothing, and still prints "processed 13 grades".
   ASan places **redzones between objects** and checks that every access stays inside the object it belongs to.
   `counts[10]` is still inside `struct stats`, so there is no redzone in the way.
   This class of bug has a name — an **intra-object overflow** — and neither Memcheck nor ASan detects it by default.
1. **Now try the undefined-behaviour sanitizer:**

   ```console
   gcc -Wall -Wextra -g -O0 -fsanitize=undefined -o histogram main.c
   ./histogram < input.txt
   ```

   ```text
   main.c:27:12: runtime error: index 10 out of bounds for type 'int [10]'
   ```

   This one catches it, because it does not work from allocations at all: it checks the index against the **declared type** of the array, which the compiler can see at the point of the write.
   Three tools, three different models of what "out of bounds" means, and only the one that knows about types is any use here.
1. **Take the array out of the struct.**
   Rewrite the program with two plain local variables:

   ```C
   int counts[10] = {0};
   int total = 0;
   ```

   Under Valgrind: still silent — Memcheck does not track stack arrays this way at all.
   Under ASan: `stack-buffer-overflow`, caught immediately, because `counts` is now its own object with a redzone after it.
   The bug did not change; only what surrounds the array did.
1. **Move `total` before the array** in the struct, rebuild the buggy version and rerun.
   Do this one — it is the most interesting experiment on the page.

   ```C
   struct stats {
   	int total;
   	int counts[NBUCKETS];
   };
   ```

   Now `counts[10]` is past the end of the struct rather than on top of `total`, so it is past the end of the allocated block as well.
   The reported total becomes correct (12) while the top bar is still one short, and Valgrind, silent a moment ago, now reports `Invalid write of size 4`.
   Nothing about the bug changed.
   Whether a memory-safety tool can see it depended entirely on the order of two fields in a struct declaration.
1. **Print less.**
   Give the debugging print a condition, `if (bucket >= NBUCKETS)`, so that it fires once instead of twelve times.
   On an input of twelve thousand grades that is the difference between a usable print and a screenful.
   A print with a condition is a conditional breakpoint you wrote yourself, and it needs no debugger session to run.
1. **Fix it a different way.**
   Instead of clamping, declare `NBUCKETS` as 11 and print the last two rows differently, or map the grade with `grade == 100 ? 9 : grade / 10`.
   Which version would you rather come back to in six months?

## Questions to answer

* **Why did Valgrind report nothing?**
  Memcheck tracks allocations: it knows which `malloc`ed block each byte belongs to and whether that block is live.
  The write landed inside a block the allocator really did hand out, so nothing improper happened as far as it can tell.
  It hit the wrong field, not the wrong block, and Memcheck does not know that fields exist.
* **`main()` validates that every grade is in `0..100`. Why was that not enough?**
  Because the index is a *second* computation.
  Validating an input constrains the input; it says nothing about a value derived from it.
* **How many buckets does a `0..100` range with ten-point buckets actually need?**
  Eleven, if every bucket is exactly ten wide — `0..9` through `90..99`, plus `100` on its own.
  The program chooses instead to make the last bucket eleven values wide, which is why it needs the clamp.
  Either answer is fine; silently using ten buckets and an unclamped `grade / 10` is not.
* **The program printed a plausible histogram the whole time. What would have had to be different about the input for the bug to be obvious?**
  Enough perfect scores to make the missing bar visible: an input of twelve 100s prints an all-zero histogram and claims to have processed 24 grades.
  A bug that hides in small numbers is not a small bug.
* **Would the bug have been caught by a test?**
  Only by one that checks the internal consistency of the output — that the bars sum to the reported total — or one that feeds a 100 and asserts the top bucket.
  A test that compares against a golden file generated by the buggy program passes forever.

## Discussion points

* **Validating the input is not the same as validating the index you compute from it.**
  The check on the grade was correct; the mapping from grade to bucket was not.
* **Valgrind's blind spot matters.**
  Memcheck works at the granularity of *allocations*, not fields.
  A write past the end of an array that is still inside the same block is invisible to it.
  This is exactly why "Valgrind is clean" is necessary but not sufficient.
* **An inclusive upper bound is a classic off-by-one generator.**
  `0..100` is 101 values, not 100.
* **Valgrind and a print answer different questions.**
  Valgrind audits the whole run for the violations it can see; a print is a microscope on one value, and needs you to aim it.
  This exercise is the case where only the microscope works, and the session's JSON parser bonus is the case where only the audit does.
* **When a value is wrong, print the values it was computed from.**
  One line of output next to the suspicious line beats an hour of reading, and it works on a machine with no debugger installed.
